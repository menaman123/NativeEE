# BUG-001 — Forward-walk soft freeze at level-chunk boundary (heap wipe after NULL alloc)

| Field | Content |
|---|---|
| **ID** | BUG-001 |
| **Title** | Chunk-load freeze: EE thread spins forever after a level-transition arena reset memsets ~29 MB from address 0 |
| **User-visible symptom** | Walking forward across a level-chunk boundary soft-freezes the game: character/game state stops, input dies, but vsync, sound mixing and presents stay alive (window still "responsive"). Deterministic ±4 vf across 7 repro legs. |
| **Scene / savestate** | `save_states/ps2state_game_crashes.ps2st` (loads vf=9281), pad script `1-999999:LY=0` (walk forward); freeze at vf≈9289-9297. |
| **Subsystem** | cdvd-loader (primary), ee-mem |
| **Root cause** | The level record parser `FUN_001bb710` read a per-record transient-batch size of `0x1001301` (16.8 MB — impossible) from the chunk record stream, because our runtime made chunk data visible out of retail order. The streaming-pool allocator `FUN_001815c0` returned NULL for that request; the game passes NULL into `FUN_002b5dd8(handle, arena_base=NULL, …)` → `FUN_002c6ce0` bzero(0 .. 0x1bae9d8), wiping the game-malloc heap's bin sentinels at 0x2ea070. The next 11.5 MB pool re-allocation walks a zeroed free-list ring (node 0 → next 0 → never reaches sentinel 0x2ea460) and spins the EE thread forever. |
| **PS2 rule violated** | CDVD/IOP read-completion ordering: the game must never observe chunk N+1's applied bytes (or a torn record stream) before chunk N's deferred-destruction drain has run — retail delivery is through the stream buffer, in order, gated by the game's own completion polls. |
| **Fix + hatch** | `[CHUNK-APPLY-ORDER]` → refined to `[CHUNK-APPLY-SCOPED]` (hle_heap.{h,cpp} `chunk_gate`, main.cpp hooks): completion visibility is held at the game's OWN visibility points on the EE thread — the `FUN_002ad110` poll hook returns "still reading", and the `HLE_FUN_002aac80` windowed-read re-entry returns 0 — until the teardown-drain edge (`FUN_00264948` / `FUN_001a1bb8` full-body run) releases it. Hatch `PS2_CHUNK_APPLY_ORDER` (unset/1 = ON; 0 = pre-fix repro). Post-refactor home: the cdvd/hle completion-visibility model (HOOK_RECLASSIFICATION §3.6). |
| **Regression test** | Walk-past harness leg on `ps2state_game_crashes.ps2st` (+2,432 vf past load, thread mix healthy `t1{busy≈207 wait≈794}`); lifecycle discriminator `PS2_S15_WATCH=c34e3c:2` shows retail MISS+MISS re-create at the boundary. INVARIANTS work item: promote the walk-past leg to a named anchor in `verify/`. |
| **Source record** | `Ps2Recomp/docs/loop_state/FREEZE_CHUNKLOAD_REPORT.md`, `FREEZE_CHUNKLOAD_IMPL.md`, `FREEZE_CHUNKLOAD_BRIEF.md` |
| **Triage tips** | If the EE thread pegs (`t1{busy=1000 wait=0}`) while sound/vsync stay alive, it is a guest-side spin, not a host deadlock — sample the process and decompile the spin site first. If guest RAM shows a giant bzero from address 0, hunt the NULL-returning allocator, then ask *why the size it read was garbage* — completion-ordering divergence upstream is the usual answer. A freeze a fixed walking distance past a load is a chunk-boundary bug, not a random hang. |
