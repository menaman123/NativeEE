# BUG-045 — Intro movies end after two pictures: the title's load-loop pump latches its abort word at an instant end of file

| Field | Content |
|---|---|
| **ID** | BUG-045 |
| **Title** | Both intro FMVs (VIVENDI.PSS, TTIDENT.PSS) tear down after their two priming pictures; the title's load-loop pump latched the SceMpeg context's abort word because the file refill reached end of file before playback started |
| **User-visible symptom** | The publisher and developer logo movies flash two frames and cut to the next scene instead of playing (≈8 s and ≈14 s of video missing); the harness reports `fmv_served_per_playback=2,2+` against the golden 201/346 |
| **Scene / savestate** | Coldboot leg, deterministic profile, `--frames 1500`: movie 1 opens at ≈frame 150, movie 2 follows; no anchor state (the FMV scene refuses savestates). Reproduce the defect by running the leg with `FmvAbortHold` uninstalled (`fmv_abort_holds=0,nohook`) |
| **Subsystem** | `cdvd-loader` (primary: instant CD delivery lets the refill outrun the movie); `ee-timing` (secondary: the pump/updater tick order) |
| **Root cause** | The title's FMV load loop `FUN_002b0ae0` (gctx = `*(0x30a700)`) calls its file refill callback `*(gctx+0x60)(buf+0x48, 0x4000)` whenever the pending byte count `gctx+0x4c` is 0 and hands every refilled window to `sceMpegDemuxPss`. Under the engine's instant CD delivery the refill reaches end of file while the player is still priming (two `sceMpegGetPicture` serves before the playing state, `FUN_002ae318`), the callback returns <0 and the pump writes `gctx+0x15c = 1` (0x2b0bc4/0x2b0bd4) — the abort word. The scene updater `FUN_002af0d8` reads it through `FUN_002b0f68` on its next tick and tears the movie down (`0x2480 → 0x400`) while the engine still holds ≈200 undelivered pictures. On retail the refill cannot outrun the bitstream ring the demux fills (`sceMpegDemuxPss` consumes only what the stream callback accepts), so end of file arrives with the last picture and the abort is the real end of the movie |
| **PS2 rule violated** | CD delivery is paced by the drive: a 16 KB stream window takes sectors' worth of time (`sceCdStRead` serves what the ring holds), so a stream consumer cannot see end of file before the data it already accepted has been consumed. `[title-idiom]` the abort word `gctx+0x15c` is the player's "refill failed" signal and the updater treats it as end of movie |
| **Fix + hatch** | Workaround (plan-sanctioned, HOOK_RECLASSIFICATION §3.1 row "FMV abort hold", class emulation-bug workaround): `games/<title>/hle/workarounds/fmv_abort_hold.{h,cpp}` (`FmvAbortHold`) wraps the scene updater `0x2af0d8`; each tick, when the handle word names a main-RAM context, `mode == mode_raw8`, the abort word is set and `MpegApi::ShouldHoldAbort(gctx)` (a started movie that has not genuinely finished), it writes the abort word back to 0 before the updater reads it. Counter `run.meta fmv_abort_holds=` (2 on the coldboot leg, one per movie). Installed in `app/host/ee_bootstrap.cpp` after `free_list_0x181560`. No hatch: the class retires through its gate (below), never by a flag. RETIREMENT GATE: a paced CD-delivery model (`DeliveryMeter` Modelled) that keeps the refill from reaching end of file before the movie ends; retire when the coldboot leg serves 201/346 with `fmv_abort_holds=0` |
| **Regression test** | ctest `FmvAbortHold` (guards, inert when `ShouldHoldAbort` is false, counter, wrapper runs the updater after the tick); ctest `RootHoldsFmvAbort` (coldboot `--frames 1500`: `fmv_served_per_playback` starts `201,346`, `fmv_pictures_served=547`, `fmv_abort_holds>=1`); ctest `MpegApi` title-cadence arm (engine window 201 for movie 1); `FmvPictureOracle` (547 golden pictures) |
| **Source record** | OLD `host_app/main.cpp:12768-12796` (`[FMV-ABORT-HOLD]` wrapper on `recompiled_functions[0x2af0d8]`, unconditional in the frozen binary); OLD `host_app/mpeg_hle.cpp:2537-2547` (`ShouldHoldAbort`); NEW `docs/phases/INTEGRATION_IMPL.md` I7.3-B/I7.3-C (INT-I73B-FMV-TWO-PICTURES, INT-I73C-ROOT-FIX-OPTION), I7.7-A |
| **Triage tips** | If `fmv_served_per_playback` reads `2,2+` while `fmv=…pictures=…` is small and the `[IPU] sceMpegDemuxPss … size=4294967295 -> 0 … abort=1` rows appear right after the two priming serves, the abort was latched at the refill's end of file: check `fmv_abort_holds=` (0 or `,nohook` = the hold is not installed; a count = it fired). If the hold fires but pictures still stop early, the engine's `ShouldHoldAbort` went false (`StreamEnded`) — look at `MpegApi` (`saw_input`, the FIFO) not at the title |
