# BUG-075 — The VU upper special-2 table decoded `func 0x3C` rows 7/8/9 (MULAq / ADDAq / SUBAq) as the `func 0x3D` column's bodies (ABS / MADDAq / MSUBAq) in both trees' interpreters; no live VU0/VU1 word of the title uses the encodings, so the lanes were unaffected

| Field | Content |
|---|---|
| **ID** | BUG-075 |
| **Title** | MULAq / ADDAq / SUBAq executed as ABS / MADDAq / MSUBAq |
| **User-visible symptom** | None observed: `scan_fd00.py` (I8.16-B, `int_work/i816b/`) counts 0 upper words with `func == 0x3C && fd in {7,8,9}` in the VU0C / VU1C sections of the artdet anchor and NEW's b2 image (`VU0C: 0 … VU1C: 0`); the title's microprograms do not use the Q column of those rows. A program that did would see ACC untouched on MULAq (ABS with ft = vf0 writes nothing) and the incoming ACC folded into ADDAq / SUBAq. |
| **Scene / savestate** | n/a (no title word reaches the rows); the pin runs synthetic one-bundle programs. |
| **Subsystem** | `vu1-hle` (the interpreter tier is shared by VU0 macro-bridge calls, the VU1 interpreter and the cached tier's generic path). |
| **Root cause** | NAMED. `VuInterpreterTier::RunSpecial2Upper` (`engine/vu/tiers/vu_interpreter_tier_upper.cpp`) tested `bc <= 1` for the ABS / MADDAq / MSUBAq arms of `case 0x07/0x08/0x09`, so the `bc == 0` column (func 0x3C) ran the 0x3D column's bodies. OLD `host_app/vu.cpp:8631-8634` carries the same decode (the tree was transplanted from it). `VuDecoder::VuUpperCanTouchHardwired` carried the same `<= 1` on row 7 (MULAq judged as "ABS writes ft"). The dependency table (`vu_decoder.cpp` rows for fd 7/8/9) was already right (MULAq reads fs only). |
| **PS2 rule violated** | VU user's manual, upper instruction special-2 table (op in the fd field; the func's low two bits select the column): row 7 = `MULAq ABS MULAi CLIP`, row 8 = `ADDAq MADDAq ADDAi MADDAi`, row 9 = `SUBAq MSUBAq SUBAi MSUBAi` — func 0x3C is the Q column: `MULAq` ACC = fs × Q, `ADDAq` ACC = fs + Q, `SUBAq` ACC = fs − Q (dest-masked, MAC flags from the result, chop rounding like their siblings). The reference interpreter's `_UPPER_FD_00_TABLE` lists `MULAq, ADDAq, SUBAq` at indices 7/8/9 (`int_work/i816b/pcsx2_VUops.cpp`). |
| **Fix + hatch** | LANDED (P8.11-A, 2026-10-04): the three `bc == 0` arms call the ACC bodies with `pipes.VisibleQ(regs)` (`acc_s(Q, OpMul/OpAdd/OpSub)` — the same per-field tail as MULAbc / ADDAbc / SUBAbc: lanes outside dest keep the incoming ACC, flags judge the result, dest lanes clamped); `VuUpperCanTouchHardwired` row 7 returns `ft == 0` only for func 0x3D. No hatch: the decode is the manual's; the cached tier reaches the same body (`generic_.RunUpper`), the VU1 HLE library matches whole program images and never decodes these rows. |
| **Regression test** | `VuSpecial2QRows` (`tests/vu/test_vu_special2_q_rows.cpp`, TIMEOUT 120): one-bundle E-bit programs, fs = {2, 4, −6, 8}, Q = 0.5, ACC = {100, 200, 300, 400} → MULAq {1, 2, −3, 4}, ADDAq {2.5, 4.5, −5.5, 8.5}, SUBAq {1.5, 3.5, −6.5, 7.5}, MULAq.xz {1, 200, −3, 400}; the 0x3D column unchanged (MADDAq {101, 202, 297, 404}, MSUBAq {99, 198, 303, 396}, ABS writes ft). RED on HEAD's decode (`int_work/p811a/vu_red_before.out`: `MULAq.xyzw … ACC = 100 200 300 400`, `ADDAq … 101 202 297 404`, `SUBAq … 99 198 303 396`, `VuSpecial2QRows: 4 failure(s)`). `VuDecodeTable` gains the three `VuUpperCanTouchHardwired` rows for 0x3C. |
| **Source record** | `docs/phases/PHASE8_IMPL.md` P8.11-A; `docs/phases/INTEGRATION_IMPL.md` INT-I816B-VU-FD00-DECODE (I8.16-B); `int_work/p811a/{vu_red_before.out,SECTION.md}`. |
| **Triage tips** | When a VU op's `bc`/column test reads `<= 1` or `>= 2`, check the manual's table column by column — the Q column (func 0x3C) and the ABS/MADDAq column (0x3D) share rows 7–9 and differ in every body. Re-run `scan_fd00.py` on a new title's images before assuming the rows are inert. |
