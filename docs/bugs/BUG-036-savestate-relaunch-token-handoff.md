# BUG-036 — Savestate LOAD relaunched the boundary thread's own tid while it still held the run token (two runners; first-to-run followed pthread start order)

| Field | Content |
|---|---|
| **ID** | BUG-036 |
| **Title** | After a `--load-state` / boundary LOAD, the resumed guest threads' first scheduling followed host pthread start order: the loading boundary thread relaunched its OWN tid on a fresh pthread while still holding the run token, so the new incarnation's `GuestEnter` found `owner_ == tid` and ran concurrently with the old one (two runners), and the old incarnation's later `GuestExit` released the NEW thread's token to whichever other thread was READY |
| **User-visible symptom** | None in play (the other resumed thread — tid 2, `SleepThread` — re-parks at once). Harness: paired legs under the deterministic profile differed in 12 `[EESCHED]` lines at the load instant (`enter tid=1 own=1 / run tid=1 / enter tid=2 / exit tid=1 own=2` vs `enter tid=1 own=2 / enter tid=2 own=2 / run tid=2`); lanes identical. A resumed thread that did real work before re-parking would make the guest state itself depend on pthread start order |
| **Scene / savestate** | any `--load-state` (measured on `save_states/ps2state_slot0_f46203_red_crystal.ps2st`, the load boundary vb=58626) |
| **Subsystem** | ee-kernel (secondary: savestate, threading) |
| **Root cause** | `savestate.cpp` DoLoad runs on the boundary guest thread (tid 1, token holder). Step 8 relaunches every saved thread via `ps2_threading::startThreadResumed` INCLUDING tid 1 itself; the new worker's `GuestEnter(1)` sees `slotFor(1)` already valid and `owner_ == 1` (the OLD incarnation) and acquires immediately — single-runner rule broken for the load window. The old incarnation then throws `ThreadExitException` (AtFrameBoundary) and its worker epilogue calls `GuestExit(1)`, which `releaseLocked(1)` → elects tid 2 while the new tid 1 still believes it holds (`t_holds` is thread_local). Which of the two arrivals happened first was host timing |
| **PS2 rule violated** | One EE, one instruction stream: after a state restore exactly one thread — the highest-priority READY one by the thbase rule — runs first, independent of how the host materialises threads |
| **Fix + hatch** | `EeRunToken::BeginRelaunch()` (loader: hand off own identity via `GuestExit(self)`, HOLD elections) → `MakeReady` every resumed thread in file order → `EndRelaunch()` (one `electLocked()` over the READY set → `relaunch-end own=2`). `GuestExit(tid)` now acts only when `t_tid == tid` (the entering thread), so the old incarnation's epilogue is a no-op. `enter` diag logged after the acquire (arrival instant is host timing). Rides `PS2_EE_RUNTOKEN` (default ON); `=0` = legacy hosting verbatim (all entry points no-op) |
| **Regression test** | paired interleave `/tmp/s125/interleave_sync.sh`: EESCHED bit-identical incl. the load window (`relaunch-begin self=1 / ready tid=1 / ready tid=2 / relaunch-end own=2 / enter tid=2 / run tid=2 / block tid=2 / enter tid=1 / run tid=1`); Phase-0 battery (every anchor leg is a load); play-env anchors 0 FATAL ×11 (`build/`). Unit coverage of the hold/handoff itself: TODO (EeSchedUnits work item) |
| **Source record** | PHASE0_IMPL.md §11.4 (this project); OLD tree `host_app/ee_sched/ee_run_token.cpp` `BeginRelaunch/EndRelaunch`, `savestate.cpp` step 8 |
| **Triage tips** | Two `run` lines for the same tid with no `block/exit` between them, or an `exit` whose `own=` names a thread that was not READY by any guest event, means a tid was re-entered while its old incarnation still held the token. Latent sibling hazard kept as-is: the old incarnation's epilogue still runs `savestate::UnregisterThreadCtx(tid)` and `info->started=false` for the relaunched tid AFTER the new one registered (harmless for the boundary thread whose ctx is passed explicitly; would bite a save-after-load of a parked relaunched thread) |
